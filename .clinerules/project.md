# FRAME — правила и конвенции для Cline (авто-подхват)

## Проект
- Monorepo: `backend/` NestJS 11 + Prisma 5.22 + PostgreSQL 15; `frontend/` React 19 + TS 5.9 + MUI 6.5 + Vite 7.
- Алиасы: db = docker postgres :5433, be = :3000, fe = :5000.
- GitHub: maxim13power-pixel/FRAME. Прод сейчас НЕ живой: Railway-сервисы не отвечают (проверено 25.10.2026),
  переезд — PROJECT_STATUS.md §12. До переезда НЕ деплоить, не поднимать DNS, не менять CORS/URL.
- Источник истины по решениям и текущему пакету — PROJECT_STATUS.md (§24 — последний пакет, §11 — 23 пункта приёмки).


## Команды (выполнять сам, не спрашивать)
- Полная проверка (be + fe): `npm run verify` в корне.
- be сборка: `npm --prefix backend run build`; dev: `npm --prefix backend run start:dev`.
- fe сборка: `npm --prefix frontend run build` (tsc -b && vite build); dev: `npm --prefix frontend run dev`.
- БД локально ТОЛЬКО `npx prisma db push`; прод ТОЛЬКО `npx prisma migrate deploy`.
- EPERM на prisma generate / query_engine = запущен dev-сервер → `taskkill /F /IM node.exe` → повтор.
- PowerShell 5.1: команды через `;`, не `&&`. Для git НЕ писать `2>&1` (stderr git = ошибка в PS).
- Пагинация вывода: `git --no-pager log` (порядок важен — `git log --no-pager` падает с unrecognized argument).
- `[System.IO.File]` / `[System.IO.Directory]` игнорируют `cd` → всегда передавать АБСОЛЮТНЫЕ пути.
- Кириллица в сообщении коммита: писать в файл UTF-8 и `git commit -F <file>` (иначе кодировка ломается).
- Долгая команда не влезает в лимит 30 с (`npm run verify` ~40 с) → запускать в фоне и опрашивать лог.


## Git (ЖЁСТКИЕ запреты)
- НЕ выполнять: `git checkout main`, `git push main`, `git merge main`.
- Работа только на ветке `cline-*` от main: `git checkout -b cline-<scope>`.
- После ЛЮБЫХ правок: `npm run verify` → 0, прежде чем отдавать дифф.
- Commit/merge/push в main делает владелец проекта; Cline может коммитить только на ветке `cline-*`.
- `git add` — только по конкретным путям. `git add -A` НЕЛЬЗЯ, если в дереве есть чужие артефакты
  (отчёты других агентов, логи, дампы, dist).
- Перед коммитом `git status --short` глазами; после — `git --no-pager log -1 --oneline` и
  `git show --name-only --pretty=format: HEAD` (убедиться, что не утащил лишнее).


## Секреты
- Только `backend/.env` и `frontend/.env` (оба в .gitignore). В коде/коммитах/отчётах — плейсхолдеры.

## Стиль правок
- Якорь не найден → СТОП (не гадать). Файл >300 строк — править кусками.
- Не выдумывать файлы/методы/API. Мёртвый код не оставлять.
- TS strict (noUnusedLocals/noUnusedParameters) → удаляй неиспользуемые импорты.
- Vite читает .env только при старте → после правки .env рестарт fe.

## Аудит (контракт, а не пожелание)
- READ-ONLY: править существующие файлы, деплоить, мигрировать БД, гонять build/verify, делать git-команды
  с изменениями — НЕЛЬЗЯ. Разрешён РОВНО ОДИН новый файл: отчёт.
- В шапке отчёта: хеш коммита (`git --no-pager log -1 --oneline`), дата, своя модель/версия (назвать самому,
  без угадывания). Отчёт без привязки к коммиту не проверяем.
- Формат: 🔴/🟡/🟢 | файл:строка | суть | почему проблема | как исправить | S/M/L | «блокирует первый платёж».
- «Попутно исправил» = нарушение контракта. Признак: `git status` показал не только отчёт → правки откатить.
- Второе мнение: аудитор НЕ читает отчёт другого аудитора по той же области до конца своего прогона
  (пишет свой файл под другим именем) — иначе теряется независимость. Расхождения вердиктов решаются
  проверкой по file:line, а не голосованием моделей.
- Внешним отчётам не верить слепо: сверять с `git --no-pager log` и текущим кодом.


## Выбор модели (имена НЕ пишем — они устаревают за 1–2 месяца)
- Любой список названий моделей здесь устареет быстрее, чем обновится правило, и приведёт к неверному
  выбору. Поэтому в правилах — только КЛАССЫ ЗАДАЧ, без брендов и версий.
- Перед выбором спроси владельца: «какие модели сейчас доступны в твоём Cline (Pro / Max / Flash)?»
  Не угадывать названия и не опираться на память о бенчмарках.
- Классы задач:
  • СУЖДЕНИЕ (аудит прав/денег/архитектуры, многофайловый разбор с противоречиями) → самая сильная доступная.
  • МЕХАНИКА (рефактор по списку, точечный фикс, конфиг, тесты) → быстрая/дешёвая.
  • РЕСЁРЧ (цены, правила сторов, лимиты платформ) → средняя; обязательны ссылки на офиц. доки + дата проверки.
- Независимость важнее «силы»: аудитор не должен быть тем, кто будет править по его отчёту.
- Две модели на одну область — только когда решение дорогое (права, деньги, деплой): основная + независимая
  другого семейства.
- Сказанное владельцем «эта модель хорошо показала себя на аудитах» — аргумент сильнее любых бенчмарков
  и моих догадок.
