# S3-миграция фото: спека и порядок (следующая задача)

> ⭐ №410 (план). Актуально на 27.11.2026. Основание: фото на Amvera пишутся в рабочую
> директорию приложения (`PHOTO_STORAGE_DIR` не задан, тома нет) — при пересборке она
> перезаписывается, то есть **фото теряются при деплое**. Плюс диск Amvera 35 ₽/ГБ против
> 3,49 ₽/ГБ в S3 Timeweb.

## 0. Что нужно от владельца до первого PUT

| Что | Где | Значение |
|---|---|---|
| Бакет S3 | `timeweb.cloud/my/storage` → создать | класс «Стандартный», **приватный**, регион РФ, пресет 1 ГБ = 1 ₽/мес |
| `S3_ENDPOINT` | панель бакета | обычно `s3.twcstorage.ru` — уточнить |
| `S3_BUCKET` | при создании | имя бакета |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | вкладка «Дашборд» | только в env, **не в git** |
| Стенд Amvera | `cloud.amvera.ru` | backend 490 ₽ + managed PG 290 ₽; `DATABASE_URL`, `JWT_SECRET`, `BILLING_ENFORCE=off` |

Офлайн-копии **до первого PUT**: `uploads/photos` (1,89 МБ) + `pg_dump -Fc`.

## 1. Диагноз (доказать на стенде, 10 минут)

1. Задеплоить `main` на Amvera → `/health` 200.
2. Залить 2–3 **копии** тестовых фото, записать `id`, размер, sha256.
3. Пересобрать/передеплоить приложение.
4. `GET /materials/photos/<id>/file` с токеном участника.

**Ожидание:** файл не найден (404/500) → диагноз подтверждён. Скриншот/лог — в §4 этого файла.

## 2. Реализация (сохраняем API-контракт)

`backend/src/photos/photo-storage.ts` уже даёт интерфейс `PhotoStorage` (`save/read/remove`)
и фабрику `createPhotoStorage()`. Меняем только реализацию:

1. `STORAGE_BACKEND=disk|s3` (по умолчанию `disk` — откат без передеплоя).
2. S3-провайдер: приватный бакет, ключи `accounts/{accountId}/objects/{objectId}/{photoId}.jpg`
   и `…-thumb.jpg`. Аккаунт/объект берём из материала (Material → Project → Object →
   владелец через `ObjectAccess.role=CUSTOMER`).
3. **Dual-read**: если у фото есть `storageKey` → читаем из S3, иначе с диска. Миграция без
   даунтайма, откат возможен, пока локальные копии живы (держим 7 дней после сверки).
4. **GET остаётся через API** (`/materials/photos/:id/file`): IDOR-проверки не меняются,
   проверено живьём (401 без токена / 404 чужой JWT / 200 участнику). Presigned GET ≤ 15 мин —
   оптимизация позже; тогда IDOR проверяется **до** выдачи URL.
5. **Квота до загрузки**: `limits.assert(accountId, 'photos')` и `'storage'` (уже есть),
   байты считаем **вместе с миниатюрой**, сверяем с S3 HEAD.
6. **Всё-или-ничего**: PUT упал → 503, записи в БД нет, локального файла-сироты нет.
   Sweep: объекты в S3 без записи в БД старше 1–48 ч → удалить.
7. Удаление фото → объект в S3 удаляется, слот и объём освобождаются.
8. **Дедуп по sha256 не делаем** (риск битых фото без refcounting). sha256 — только контрольная
   сумма при миграции.

## 3. Скрипт миграции 20 фото

`backend/scripts/migrate-photos-to-s3.js`:

1. Взять все `material_photos`, где `storageKey IS NULL`.
2. Для каждого: прочитать локальный файл (полный + миниатюра), посчитать sha256, загрузить в S3,
   сверить размер из S3 HEAD с локальным (включая миниатюру).
3. Записать `storageKey` (и `thumbKey`) в БД только после успешной сверки.
4. Идемпотентный: повторный запуск пропускает уже перенесённые.
5. Локальные копии **не удалять** — отдельным флагом `--prune` после 7 дней.

## 4. Критерии приёмки

| # | Критерий | Как проверяем |
|---|---|---|
| 1 | 20/20 фото перенесены, sha256 и размеры совпали | лог скрипта + сверка с S3 HEAD |
| 2 | **Редеплой-тест зелёный**: загрузил → пересобрал → GET 200, байты совпали | вручную на стенде |
| 3 | Сирот нет: 2 параллельных upload при 4/5 → 1 запись в БД и **1 файл** | concurrency-тест |
| 4 | Удаление фото удаляет объект в S3 и освобождает слот | API + S3 HEAD 404 |
| 5 | `STORAGE_BACKEND=disk` возвращает старое поведение (пока копии живы) | переключение env |
| 6 | Квота считает миниатюру; `LIMIT_STORAGE` срабатывает до загрузки | тест на Free/Прорабе |
| 7 | Бакет приватный: прямой URL без подписи → 403 | `curl` без подписи |
| 8 | Egress учтён в юнит-экономике (1,3 ₽/ГБ сверх 100 ГБ/мес) | `docs/PRICING.md` §3 |

## 5. Порядок работ

1. Бакет Timeweb + ключи в env (владелец).
2. Стенд Amvera + деплой `main` + дамп БД (владелец), диагноз потери фото (§1).
3. S3-адаптер + dual-read + sweep (агент), unit-тесты на ключи и выбор бэкенда.
4. Скрипт миграции, перенос 20 фото, сверка (§3).
5. Редеплой-тест (§4 п.2) — **главный критерий**.
6. Только после этого: `BILLING_ENFORCE=shadow` на стенде, concurrency-тесты, синтетика шести
   стен, фронт с плашками, затем `on`.

## 6. Что НЕ входит

- Дедупликация по sha256 (бэклог, account-scoped + refcounting).
- CDN перед S3.
- `pg_dump` → S3 (отдельная задача после миграции, с проверкой восстановления).
- Ресайз на лету.
