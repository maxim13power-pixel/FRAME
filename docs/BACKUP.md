# Бэкапы и восстановление (FRAME)

> ⭐ №395, 25.11.2026. Коротко: **бэкап = дамп базы + архив фото**. Скрипт делает и то, и
> другое одной командой, проверяет целостность, ведёт лог и хранит последние N копий.
> Восстановление проверяется drill'ом (реальное разворачивание в отдельную базу со сверкой).

## Зачем

База живёт на сервере, и с ней может случиться что угодно: ошибочный деплой, случайное удаление
объекта, сбой хостинга, шифровальщик. Без копии данные теряются навсегда — сметы, фиксации
объёмов, история. Плюс персональные данные (телефон, e-mail) — по 152-ФЗ их сохранность
обязанность оператора.

**Важно:** фотофиксации хранятся **не в базе**, а на диске (`PHOTO_STORAGE_DIR`, по умолчанию
`backend/uploads/photos`). Поэтому дамп базы без архива фото — неполный бэкап.

## Что делает `db:backup`

```bash
cd backend
npm run db:backup                      # база + фото, в <repo>/backups, хранить 14 копий
node scripts/db-backup.js --out D:\backups --keep 30
node scripts/db-backup.js --no-files   # только база (например, если фото уже в S3)
```

1. `pg_dump -Fc` — сжатый custom-формат (восстанавливается выборочно: таблица/схема).
2. Проверка дампа: сигнатура `PGDMP`, оглавление через `pg_restore -l` (читаемость архива),
   `sha256` в файл рядом.
3. Архив фото: `tar.gz` из `uploads/`, проверка оглавления (`tar -tzf`), `sha256` рядом.
4. Лог `backups/backup.log` (дата, файлы, размеры, время, хеши).
5. Ротация: остаются последние N дампов и N архивов фото (`--keep`, по умолчанию 14).

Режим выбирается сам: если запущен контейнер `frame_postgres` — работаем через `docker exec`
(dev), иначе — локальные `pg_dump`/`pg_restore`/`psql` (сервер). Принудительно: `DB_PG_MODE=docker|local`.

## Что делает `db:restore` (и как проходит drill)

```bash
cd backend
npm run db:restore -- --file ../backups/frame_db-2026-11-25_10-44.dump
# по умолчанию разворачивает в <база>_check и сверяет ВСЕ таблицы с источником
```

- Защита от ошибки: цель не может совпадать с источником; имя цели обязано оканчиваться на
  `_check` (или `_restore`), иначе нужен явный `--force`.
- Пересоздаёт целевую базу и разворачивает дамп.
- Сверяет количество строк по всем таблицам (кроме служебной `_prisma_migrations`) и падает,
  если есть расхождения.
- Фото восстанавливаются вручную (см. ниже) — их в базу не заливаем.

**Чек-лист drill** (раз в месяц и после каждого изменения схемы/деплоя):
1. `npm run db:backup` → в выводе есть размер, число записей, `sha256`, файлы фото.
2. `npm run db:restore -- --file <свежий дамп>` → «✅ все таблицы совпали».
3. Открыть `backups/backup.log`, записать дату и тайминги в таблицу ниже.
4. Удалить проверочную базу (`DROP DATABASE frame_db_check`) — чтобы не занимала место.

### Замер 25.11.2026 (dev: frame_db, Docker `frame_postgres`, 32 таблицы)

| Шаг | Время | Размер / объём |
|---|---|---|
| `pg_dump -Fc` | 239 мс | 197.9 КБ, 342 записи в архиве |
| Проверка дампа (`pg_restore -l`) | 141 мс | — |
| Архив фото (`tar.gz`) | 82 мс | 1.93 МБ, 40 файлов |
| Restore в `frame_db_check` | 628 мс | 32 таблицы, 3976 строк |
| Сверка количества строк | 651 мс | расхождений 0 |

Данные крошечные (2 МБ с фото), поэтому цифры — «секунды». На проде с ростом данных смотреть
на размер дампа и время restore: при restore > 5 минут стоит подумать о PITR/реплике.

## Политика (что и как часто)

| Когда | Что | Где хранится |
|---|---|---|
| Ежедневно (ночью) | `db:backup` (база + фото), 14 копий | каталог `backups` на сервере/томе |
| Перед каждым деплоем и миграцией | `db:backup` вручную | тот же каталог |
| Еженедельно | копия последнего дампа **вне сервера** (объектное хранилище, диск владельца) | offsite |
| Ежемесячно | restore drill + запись в таблицу выше | — |

- Amvera PG даёт **свои** автобэкапы (3 последних + 3 ручных), но **без PITR**; restore там
  создаёт новый кластер → придётся менять `DATABASE_URL`. Наши дампы — независимая страховка.
- Offsite-копия обязательна: если сервер умрёт вместе с диском, локальные копии уедут с ним.
- Ответственный за drill — владелец продукта; выполняет и записывает — разработчик (Cline/я).

## Восстановление на проде (порядок)

1. **Не восстанавливать поверх живой базы.** Сначала `db:backup` текущего состояния (даже
   если оно «плохое» — это доказательство).
2. Развернуть дамп в **новую** базу (на Amvera — через панель/`pg_restore` в отдельную БД).
3. Сверить количество строк (тот же принцип, что в `db:restore`).
4. Переключить `DATABASE_URL` приложения на восстановленную базу → перезапустить.
5. `npx prisma migrate status` → «up to date» (дампам из этой схемы миграции не нужны).
6. Фото: распаковать `photos-*.tar.gz` в `PHOTO_STORAGE_DIR` (проверить права и владельца).
7. Smoke: вход, дашборд, смета, фиксация, экспорт PDF, открыть фото.

## Чего не делать

- Хранить дампы в git (в `.gitignore` уже закрыто) или в публичном каталоге.
- Восстанавливать «на живую» без новой базы.
- Игнорировать расхождения в сверке («почти совпало» = дамп снят во время записи → снять заново).
- Забывать про `PHOTO_STORAGE_DIR` на сервере: если это не постоянный том, фото исчезнут при
  передеплое (в бэкапе останутся только те, что были на момент снятия).

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| `pg_dump` не найден | поставить PostgreSQL client или запустить Postgres в Docker (тогда скрипт сам пойдёт через `docker exec`) |
| `database ... is being accessed by other users` | закрыть соединения: `pg_terminate_backend` (скрипт restore делает это сам для `_check`-баз) |
| `P1001` у Prisma | `DATABASE_URL` должен быть `127.0.0.1`, не `localhost` |
| Дамп «подозрительно мал» | проверить `DATABASE_URL` и права; посмотреть вывод `pg_dump` в логе |
| Кириллица в логах «кракозябрами» | смотреть в UTF-8 (VS Code/PowerShell с `chcp 65001`); сами данные в дампе в UTF-8 |
