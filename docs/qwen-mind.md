## 0. TL;DR — 10 строк

1. **Делаем импорт в проект напрямую, а не через шаблон сметы.** Шаблон (`EstimateTemplateItem`, `schema.prisma:468–483`) физически не хранит `article` и `note` — половина ценности спецификации теряется на первом же шаге.
2. **Модуль шаблонов сейчас небезопасен**: `apply()` не проверяет роль (`estimate-templates.service.ts:105–134`), а `list()` отдаёт цены без `stripPrices` (`:40–46`). Строить импорт поверх него — значит унаследовать дыру. Чиним отдельно, до импорта.
3. **Парсим и матчим на сервере.** `exceljs@^4.4.0` уже в зависимостях (`backend/package.json:41`) и уже используется (`reports/xlsx.service.ts:4`). `multer@2.0.2` лежит транзитивно, но **`@types/multer` не установлен** — без него TS-сборка не соберётся.
4. **Цены из файла — не истина.** `unitPrice`/`materialUnitPrice` — снапшот, который сервер копирует из `PriceItem` (`materials.service.ts:151–170`). Цена из файла участвует только в одном решении: «создать личную расценку по этой цене» или «взять справочную».
5. **Нужна сущность `ImportBatch` + поля `Material.importBatchId` / `externalKey`.** Без них нет ни отката, ни ответа «кто залил эти 300 строк», ни честной идемпотентности. Это одна миграция (последняя в репо — `20261004165442_add_audit_log`).
6. **`POST /materials/bulk` как основной канал не годится**: в `main.ts:5–36` лимит тела не поднят, express режет JSON на 100 КБ, а 500 строк ≈ 120–150 КБ. Загрузка — `multipart/form-data`, commit — компактный JSON по `batchId` (без самих строк).
7. **Commit — одна транзакция, всё или ничего.** «Половина сметы залилась» хуже, чем «не залилось ничего»: прораб не сможет отличить свои 300 строк от 187 чужих.
8. **Через `ChangeRequest` импорт не гоним.** `ADD_ROW` — одна заявка на одну строку с аппрувом вторым лицом и запретом согласовать свою (`change.service.ts:173–175`). 300 строк = 300 заявок. Согласование имеет смысл **на уровне партии**, и это отдельная фича, а не MVP.
9. **Реалистичная оценка — 9–11 рабочих дней** на описанный объём с тестами, из них первый полезный срез — 4 дня. «2,5–3 дня» — недооценка втрое; причина не в коде, а в грязных файлах и матчинге.
10. **Главная продуктовая ошибка предыдущего предложения** — проектировать «заполнение нашего шаблона». Прораб приносит **чужой** Excel. Если 300 строк надо перебить в нашу форму, мы автоматизировали не ту работу. Приём произвольного файла с авто-определением колонок — условие выживания фичи, а не «nice to have».

## 1. Что я увидел в коде: ограничения и скрытые долги

### 1.1 Как устроена строка сметы (база для всех решений)

`Material` (`schema.prisma:101–135`) — это **гибрид**: одна строка = одна работа + один материал.

| Поле | Строки | Смысл |
|---|---|---|
| `name`, `article?`, `unit` | `:103–105` | идентификация; `unit` — enum `Unit` (`:88–99`), 10 значений |
| `specQuantity` | `:106` | план, `Decimal(14,3)` |
| `totalUsed`, `lastEntry`, `lastEntryDate` | `:107–109` | факт, считается из `MaterialFix` |
| `progressPercent` | `:111` | `Float`, `Math.round(totalUsed / specQuantity * 100)` |
| `isSpecLocked` | `:112` | **`@default(true)`** — см. §1.4, это боль |
| `priceItemId?`, `unitPrice`, `totalCost` | `:115–118` | работа: ссылка + снапшот цены + `totalUsed × unitPrice` |
| `materialItemId?`, `materialUnitPrice`, `materialTotalCost` | `:121–124` | материал: то же |
| `projectId` | `:126–127` | `onDelete: Cascade` |
| индексы | `:133` | **только `@@index([projectId])`** |

Ключевое следствие: **плановая стоимость не хранится**. Она считается на лету как `unitPrice × specQuantity` (`Materials.tsx:338–339`), а `totalCost`/`materialTotalCost` — «на текущий момент», от факта (`materials.service.ts:247–248`). Значит при импорте `totalCost = 0` — это **правильно**, а не баг: факта ещё нет.

### 1.2 Снапшоты цен: почему файл не может быть источником денег

`materials.service.create()` (`:143–190`):
- `:147–149` — `VIEWER` получает 403 «Наблюдатель не может создавать материалы»;
- `:151–159` — если пришёл `priceItemId`, сервер читает `PriceItem`, проверяет `isActive` и **копирует `price` в `unitPrice`**;
- `:160–170` — то же для `materialItemId`;
- `:171–187` — `create` **без `isSpecLocked`** → срабатывает дефолт `true`.

В `CreateMaterialDto` (`create-material.dto.ts:24–55`) ценовых полей **нет вообще**. Это принцип: клиент говорит «какая расценка», сервер говорит «сколько денег». Импорт обязан его сохранить, иначе появится два источника правды о деньгах и вечный спор «почему в смете не та цена».

### 1.3 🔴 Долг: `create()` не проверяет `kind` и `ownerId` расценки

`materials.service.ts:152` делает `priceItem.findUnique({ where: { id } })` — **без фильтра по владельцу и типу**. Проверяются только существование и `isActive`.

Практические следствия:
- можно прицепить к «работе» (`priceItemId`) расценку типа `MATERIAL` — смета начнёт считать материал как работу;
- можно передать `id` **чужой личной** расценки (`ownerId = другой userId`) и получить её цену в снапшоте. Личный справочник (`schema.prisma:166`) задуман приватным, а фактически читается по `id`. То же в `update()` (`:507–514`, `:529–537`).

Для сравнения: `change.service.ts:84–110` и `:228–266` проверяют **и `kind`, и `isActive`, и `OR [{ownerId: null}, {ownerId: userId}]`**. Правильный образец в проекте уже есть — просто не применён в основном пути.

**Вывод:** импорт не имеет права переиспользовать `create()`. Он резолвит расценки сам, с обязательным фильтром `kind` + `ownerId`, и не доверяет `id` из файла. Попутно закрывается дыра: через импорт нельзя зондировать чужие личные цены.
