## 4. Правила лимитов (обязательны к реализации)

1. Лимит проверяется **только при создании**: новый объект, новая строка, приглашение
   участника, загрузка фото. Уже введённые данные не блокируются и не удаляются.
2. При достижении лимита — понятный отказ с машинным кодом: `LIMIT_OBJECTS`, `LIMIT_ROWS`,
   `LIMIT_PHOTOS`, `LIMIT_SEATS`, `PLAN_REQUIRED` + текст «что даёт следующий тариф».
3. **Grace 7 дней** после превышения: разрешаем дозаписать до +10 % (фиксация объёма
   не должна ломаться на объекте), показываем баннер с предложением тарифа.
4. Экспорт: PDF на Free — 3/мес с водяным знаком на каждой странице, счётчик сбрасывается
   1-го числа. XLSX на Free не ограничен (снимает возражение «Excel бесплатно»).
5. Импорт (Excel/прайс, «копировать смету») **тоже** проверяет лимит строк — иначе лимит
   обходится импортом.
6. История фиксаций старше лимита не удаляется, а сворачивается в месячные агрегаты
   (`MaterialFixMonthly`), в UI — «архив доступен на Бригаде».

## 7. Анти-абьюз

1. **Free без фото** — главный источник расходов закрыт решением владельца.
2. Ключи S3 выдаём **presigned PUT** только после проверки квоты; POST-policy ограничивает
   размер файла (≤ 8 МБ).
3. Серверная проверка `magic bytes` + повторное сжатие через sharp, если файл > 500 КБ
   или сторона > 1600 px (клиентскому сжатию не доверяем).
4. Дедупликация по `sha256`: одно фото на несколько фиксаций = один объект в S3.
5. Экспорт: 1 активная задача на аккаунт; > 1 000 строк — асинхронно (очередь pg-boss),
   результат кэшируется в S3 на 24 ч по хешу фильтров.
6. Регистрация: 1 Free на подтверждённый e-mail, капча после 3 неудач (уже есть в
   `login-throttle.service.ts`), алерт при > 20 экспортов/сутки с одного аккаунта.

### 8.3. Этап 1 — что уже сделано (№405/№406)

- `POST /billing/exports/pdf/authorize` (JWT): возвращает `{ allowed, accountId, watermark, maxRows,
  rows, token, expiresAt, used, limit, left, reused }`.
- **Квота — аккаунта владельца объекта** (№406): приглашённый прораб печатает за счёт плана
  владельца (`resolveProjectAccount`: CUSTOMER объекта), в токене/строке авторизации остаётся
  `actorUserId` только для аудита. Проверено живьём: прораб (id 65) печатает проект `s@mail.ru` →
  `accountId 45`, `used 1`, `watermark false`, `maxRows 10 000`; счётчик владельца 1, прораба 0.
- **`rows` считает сервер** (`COUNT(*)` по проекту), клиентскому `rowCount` больше не доверяем.
- **Хеш от данных**: проект + фильтры + число строк + `max(material.updatedAt)` — правка строки
  делает документ другим (новое списание), повтор без правок — бесплатен.
- **Столбление + списание в одной транзакции** (№406): при лимите — откат, осиротевших
  «бесплатных» авторизаций не бывает; проверено гонкой двух параллельных запросов одного
  документа: ровно одно списание (`used 2`, второй ответ `reused: true`).
- Токен: `HMAC-SHA256(accountId|periodKey|payloadHash|exp)`, 15 минут, секрет `EXPORT_TOKEN_SECRET`
  (фолбэк `JWT_SECRET`).
- Гигиена: при авторизации удаляются строки прошлых месяцев (`periodKey < current`).
- Знак (`watermark`) и `maxRows` приходят с сервера.

### 8.4. Решения, зафиксированные после ревью

1. **Повторная печать того же документа в том же месяце — бесплатна** (осознанно: прораб
   отправляет смету двум заказчикам и не должен платить дважды). Разные документы = разные хеши.
2. **PDF — до `maxExportRows` строк за документ** (Free 150 / Прораб 5 000 / Бригада 10 000);
   **XLSX — до лимита строк плана** (вкладку не вешает). В UI пишем «PDF по частям».
3. **Клиентская генерация = мягкий лимит**: модифицированный клиент может обойти authorize;
   реальная защита — серверный счётчик. Жёсткий enforcement — только при серверном рендере (v2).
4. **Grandfather — только до cutoff** миграции `2026-11-26T07:28:43Z` (+ `skipDuplicates`);
   проверено: аккаунт, созданный после, остаётся Free, grandfather-подписок 3.
5. ~~**Окно правки на Free (10 минут, тот же проект)**~~ — **отклонено** по итогам ревью:
   правка существующей строки счётчики не меняет (лимит только при создании), а таймерная
   логика противоречит правилу «данные не блокируются». Замена фото = удалить + загрузить,
   слоты работают как надо.

| **Индексы под `COUNT(*)`** | `object_access(userId, role)` + существующие `materials(projectId)`, `material_photos(materialId, createdAt)` |
| **Лог shadow: `actor=` и `endpoint=`** | Добавлено: `[billing:would-block-export] mode=… account=… actor=… project=…`; в `limits` — `would block LIMIT_* account=… plan=… used=… limit=… mode=…` |
| **Тексты апселла с числами из БД** | Принято к работе: сейчас числа в тексте, на этапе 1.5 переведём на шаблоны из `plans` (чтобы менять лимиты без правки текста) |
| **Shadow на текущей базе пуст (все TEAM)** | Принято: выход из shadow — синтетический прогон пяти стен на временном Free + 2–3 живых прораба на Free; «0 срабатываний на TEAM» — лишь проверка отсутствия багов подсчёта |
| **Чистка авторизаций прошлых месяцев** | Сделано в №406 (`periodKey < current`) |
| **Grandfather-cutoff** | Сделано ранее; проверено отдельным скриптом (новый аккаунт остаётся Free, grandfather-подписок 3) |

Осталось по этапу 1: плашки «осталось N» и 6 триггеров апселла во фронте (и вызов
`authorize` перед генерацией PDF), нормализация alias-почт и блок-лист одноразовых доменов,
лимит регистраций на IP, concurrency-тест в регрессии.

### 8.5. Enforcement лимитов (№407) — сделано, режимы

Единая точка проверки — `backend/src/billing/limits.service.ts`:
`check(accountId, kind, add)` → `{ allowed, code, limit, used, left, message }`,
`assert(...)` → 403 с машинным кодом (в режиме `on`).

| Режим `BILLING_ENFORCE` | Поведение |
|---|---|
| `off` (по умолчанию) | ничего не считаем, продукт работает как раньше |
| `shadow` | считаем и пишем `would block LIMIT_* account=… plan=… used=… limit=…`, **не блокируем** |
| `on` | блокируем: 403 `{ code: LIMIT_OBJECTS \| LIMIT_ROWS \| LIMIT_PHOTOS \| LIMIT_STORAGE \| LIMIT_WRITERS \| LIMIT_VIEWERS, message: <текст апселла> }` |

Встроено: создание объекта (`objects.service.create`), создание строки сметы
(`materials.service.create`), массовое дублирование строк (`bulkDuplicate`, с учётом количества),
загрузка фото (`photos.service.upload` — слоты на Free + объём на платных). Квота везде —
**аккаунта владельца объекта**, не автора действия.

Проверено живьём (Free-аккаунт): `shadow` — 1-й объект 201, 2-й 201 + лог
`would block LIMIT_OBJECTS account=966 plan=FREE used=1 add=1 limit=1 mode=shadow`;
`on` — 1-й объект 201, 2-й **403 `LIMIT_OBJECTS`**. После проверок бэкенд возвращён в `off`,
тестовый аккаунт удалён, база в базовом состоянии (4 объекта / 18 проектов / 484 строки).

## 12. Хранилище фото: где лежит и что будет при редеплое (ответ ревью №409)

**Факт по конфигурации:** `backend/amvera.yaml` не монтирует постоянный том, переменной
`PHOTO_STORAGE_DIR` в окружении нет → `photo-storage.ts` использует
`path.resolve(process.cwd(), 'uploads', 'photos')`, то есть **папку внутри рабочей директории
приложения**. На Amvera рабочий каталог относится к артефакту сборки: при пересборке/редеплое
он пересоздаётся, поэтому **фото в `uploads/photos` не переживают деплой**. Плюс они не видны
второму инстансу (нет общего хранилища) и не попадают в бэкап БД.

**Вывод:** это не «оптимизация на будущее», а риск потери данных уже сейчас (пусть фото пока
и тестовые). Плюс квоты в ГБ на диске Amvera стоят 35 ₽/ГБ против 3,49 ₽/ГБ в S3 — разница ~10×.

**Решение владельца (ожидается):** миграция фото в S3 (Timeweb, приватный бакет,
`STORAGE_BACKEND=disk|s3` для отката) — или, как временный компромисс на старте, квоты
1 ГБ Pro / 5 ГБ Team на диске с явной пометкой «до миграции S3».

**Пока S3 не сделан:** продавать фото-объёмы (3 ГБ / 15 ГБ) нельзя — обещание не обеспечено
ни экономикой, ни сохранностью.

## 13. TOCTOU: где блокировка есть, а где её нет (№409)

| Путь | Блокировка |
|---|---|
| Создание объекта | `pg_advisory_xact_lock(hashtext('limit:objects:<id>'))` в транзакции + in-process очередь |
| Создание строки сметы | `pg_advisory_xact_lock(hashtext('limit:account:<id>'))` **внутри** транзакции создания, проверка лимита там же |
| Импорт XLSX | тот же ключ `limit:account:<id>` внутри транзакции импорта (до записи строк) |
| Загрузка фото, приглашение участника | in-process очередь (`runSerialized`) — достаточно для одного контейнера; при нескольких инстансах добавить `limit:account:<id>` в их транзакции (отмечено как TODO) |

Единый ключ `limit:account:<id>` для строк и импорта — именно для того, чтобы эти пути
**блокировали друг друга**: они делят одну квоту строк, и без общей блокировки два параллельных
запроса (строка + импорт) читают одинаковый `used` и вместе перескакивают лимит.
Объекты используют отдельный ключ `limit:objects:<id>`, потому что у них отдельный счётчик —
пересечения нет.

**Фото и приглашения (№409):** загрузка фото проверяет слоты повторно **внутри транзакции**
под `pg_advisory_xact_lock('limit:account:<id>')` — два параллельных upload не дадут 6 фото на Free.
Приглашения пока защищены in-process очередью (`runSerialized`); для мультиинстанса — тот же
ключ в их транзакции, отмечено в коде.

### 13.1. Почему индекс `objects(accountId)` не применим

У модели `Object` **нет** поля `accountId`: принадлежность аккаунту определяется через
`ObjectAccess` (`userId` + `role = CUSTOMER`).

**Проверено на живой БД (26.11.2026):**
- у `s@mail.ru` в `object_access` только роль `CUSTOMER` — 4 записи на 4 объекта, **дублей нет**
  (`GROUP BY objectId HAVING count(*) > 1` → пусто). Значит `COUNT(*)` без `DISTINCT` корректен,
  а `role = 'CUSTOMER'` — правильный фильтр владельца квоты;
- `EXPLAIN` на 7 строках даёт Seq Scan — это нормальное поведение планировщика на крошечной таблице;
- при `SET enable_seqscan = off` план переключается на **`Index Scan using object_access_userId_role_idx`**,
  а подсчёт строк — на **`Index Only Scan using materials_projectId_externalKey_key (projectId = p.id)`**.
  То есть индексы на месте и будут использованы при росте данных; seq scan сейчас — не проблема схемы.

**Роли и квота (зафиксировано):**

| Роль в `ObjectAccess` | Пишет? | Владелец квоты аккаунта | В какой лимит считается |
|---|---|---|---|
| `CUSTOMER` (создатель/админ объекта) | да | **да** | `writers` (если не владелец аккаунта) |
| `FOREMAN` | да | нет | `writers` |
| `VIEWER` | нет (read-only) | нет | `viewers` |

Виральный канал на Free — именно `VIEWER`; в текстах: «покажи наблюдателю», не «заказчику».

### 13.2. Дедупликация по sha256 — в бэклог, не в миграцию

Отклонено для миграции: экономия ≈ 1 ₽/мес на Прораба, а риск — два фото ссылаются на один объект,
и удаление одного ломает доказательную базу (нужен refcounting). `sha256` остаётся **контрольной
суммой сверки** при миграции 20 фото, а не ключом дедупликации. Дедуп — после релиза,
account-scoped, с refcounting.

### 13.3. S3 — что войдёт в спеку (сводно)

1. `STORAGE_BACKEND=disk|s3` — откат без передеплоя; локальные копии держим 7 дней после сверки.
2. **Dual-read**: есть `storageKey` → S3, нет → диск (миграция без даунтайма).
3. Приватный бакет, ключи `accounts/{accountId}/objects/{objectId}/{photoId}.jpg` + thumb.
4. `GET /materials/photos/:id/file` — **через API** (proxy), IDOR-проверки сохраняются.
   Presigned GET (≤ 15 мин) — оптимизация позже; при переходе на presigned IDOR проверяется
   **до** выдачи URL.
5. Квота проверяется **до** загрузки; байты считаем вместе с миниатюрой, сверяем с S3 HEAD.
6. Сбой S3 при загрузке → 503, записи в БД нет, файла-сироты нет (всё-или-ничего);
   sweep: объекты без записи в БД старше 1–48 ч удаляются.
7. Удаление фото → объект в S3 удаляется, слот освобождается.
8. Миграция 20 фото: загрузка → сверка sha256 и размера → проставить `storageKey` → локальные
   копии удалить только после сверки. Скрипт идемпотентный.
9. **Редеплой-тест** — главный критерий: загрузил фото → пересобрал → GET 200, байты совпали.
10. Egress Timeweb S3 (1,3 ₽/ГБ сверх 100 ГБ/мес) — в юнит-экономику как переменную.
11. `pg_dump` → S3 — отдельной задачей после миграции, с проверкой восстановления.
