## 4. Правила лимитов (обязательны к реализации)

1. Лимит проверяется **только при создании**: новый объект, новая строка, приглашение
   участника, загрузка фото. Уже введённые данные не блокируются и не удаляются.
2. При достижении лимита — понятный отказ с машинным кодом: `LIMIT_OBJECTS`, `LIMIT_ROWS`,
   `LIMIT_PHOTOS`, `LIMIT_SEATS`, `PLAN_REQUIRED` + текст «что даёт следующий тариф».
3. **Grace 7 дней** после превышения: разрешаем дозаписать до +10 % (фиксация объёма
   не должна ломаться на объекте), показываем баннер с предложением тарифа.
4. Экспорт: PDF на Free — 3/мес с водяным знаком на каждой странице, счётчик сбрасывается
   1-го числа. XLSX на Free не ограничен (снимает возражение «Excel бесплатно»).
5. Импорт (Excel/прайс, «копировать смету») **тоже** проверяет лимит строк — иначе лимит
   обходится импортом.
6. История фиксаций старше лимита не удаляется, а сворачивается в месячные агрегаты
   (`MaterialFixMonthly`), в UI — «архив доступен на Бригаде».

| Функция | Статус в коде | Что делать |

## 7. Анти-абьюз

1. **Free без фото** — главный источник расходов закрыт решением владельца.
2. Ключи S3 выдаём **presigned PUT** только после проверки квоты; POST-policy ограничивает
   размер файла (≤ 8 МБ).
3. Серверная проверка `magic bytes` + повторное сжатие через sharp, если файл > 500 КБ
   или сторона > 1600 px (клиентскому сжатию не доверяем).
4. Дедупликация по `sha256`: одно фото на несколько фиксаций = один объект в S3.
5. Экспорт: 1 активная задача на аккаунт; > 1 000 строк — асинхронно (очередь pg-boss),
   результат кэшируется в S3 на 24 ч по хешу фильтров.
6. Регистрация: 1 Free на подтверждённый e-mail, капча после 3 неудач (уже есть в
   `login-throttle.service.ts`), алерт при > 20 экспортов/сутки с одного аккаунта.

### 8.1. Что именно сделано на этапе 0 (№404)

- Миграция `20261126072843_billing_plans`: таблицы `plans`, `subscriptions`, enum'ы
  `PlanCode` / `SubscriptionStatus` / `SubscriptionSource`. Ничего не удалено, только добавлено.
- Миграция `20261126074411_billing_usage_index`: индекс `object_access(userId, role)` под
  подсчёт использования по тарифу.
- `backend/scripts/seed-plans.js` (`npm run db:seed:plans`): идемпотентно создаёт 3 тарифа
  с лимитами из §2 и выдаёт **grandfather** (Бригада, бессрочно) **только аккаунтам,
  созданным до миграции** (`createdAt < 2026-11-26T07:28:43Z`), с `skipDuplicates`.
  Аккаунты, зарегистрированные позже, остаются на Free — повторный запуск сидов никому
  не дарит Бригаду.
- `backend/src/billing/`: `BillingService` (действующий план с учётом срока/grandfather/отмены,
  использование через `COUNT(*)`, **атомарный** `consumePdfExport` одним `UPDATE … WHERE`,
  поэтому гонка на границе лимита и месяца невозможна), `BillingController`
  (`GET /billing/me`), `BillingModule` в `app.module.ts`.
- Флаг `BILLING_ENFORCE` с тремя режимами: `off` (по умолчанию) / `shadow` (считаем и логируем,
  не блокируем) / `on` (блокируем с кодом `LIMIT_*`).
- Аккаунт без строки `subscriptions` детерминированно считается **Free** (это же правило
  работает для новых регистраций — строку подписки создаём только при оплате/выдаче).
- Поведение продукта НЕ изменилось: лимиты не применяются, данные не трогаются.

## 10. Итог внешнего ревью (26.11.2026): что принято, что отклонено

Ревью двух независимых агентов + моя проверка по коду и данным.

**Принято:**
1. **5 фото на Free** (оба агента и я) — расходы ≈ 0, демонстрация ценности сохраняется.
2. **Никакого TTL** — данные не удаляем по таймеру (согласен со вторым ревью: экономия
   270 ₽/мес не стоит риска «где мои фото»).
3. **S3 считать по пресетам**: 10 ГБ = 79 ₽, 100 ГБ = 349 ₽ (3,49 ₽/ГБ), а не по 1 ₽/ГБ.
4. **Явные лимиты вместо «без лимита»** на платных PDF: 200/1 000 в месяц.
5. **Фискализация — переменная, не фикс**: у ЮKassa чеки ≈ +1 % к комиссии; своя касса
   (1,5–3 тыс. ₽/мес) — только при обороте ≳80–220 тыс. ₽/мес.
6. **Старт оплаты по счёту** (ООО/ИП, без кассы), ЮKassa + СБП — как только появится
   первое физлицо-плательщик (физлицу чек обязателен по 54-ФЗ).
7. **Существующим аккаунтам — Бригада навсегда**: их 3 (`s@`, `1@`, `q@mail.ru`), стоимость ≈ 0.
8. **При даунгрейде — read-only, данные не удаляем** (правило №7 в §4).

**Отклонено (с обоснованием):**

| Предложение ревью | Почему отклоняем |
|---|---|
| «5 фото пожизненно» (вместо активных) | Та же защита хранилища (одновременно лежит 5 файлов), но нужен отдельный счётчик «за всё время». «5 активных» проще и дружелюбнее: неудачный снимок можно заменить |
| «Прораб 7 000 строк» | Обосновано допущением P90 = 700 строк, которого мы не измеряли. Наши данные — синтетика: 3 пользователя, медиана 4 строки/проект, P90 32, максимум 400 (тестовая смета). Лимиты живут в БД → поменяем одной строкой после живого теста |
| «Очередь экспорта (pg-boss), кэш экспорта в S3, 1 экспорт на аккаунт» | Экспорт сметы PDF/XLSX генерируется **в браузере** (pdfmake + xlsx-js-style на фронте), серверного CPU он не тратит. Серверный `exceljs` — только импорт, где лимиты уже есть (`xlsx-guard`). Очередь и кэш — преждевременная сложность |
| «Капча нужна на регистрации» | **Уже есть**: Yandex SmartCaptcha, в prod обязательна (`auth.service.register`), плюс лимит 3 кода/час на e-mail и 5 попыток ввода. Незакрытое — нормализация alias-почт (gmail `+`/точки) и блок-лист одноразовых доменов: дешёвый фикс в этап 1 |

**Поправки к нашей арифметике (приняты):** маржа на 100 % выбора квот ниже — Прораб ≈ 15 ₽
себестоимости (84–86 % маржи), Бригада ≈ 75 ₽ (82–86 %); безубыточность 3 платящих на счёте
и 4–6 после подключения ЮKassa с чеками (фикс растёт на email/домен/staging).
