# RFC: «Импорт сметы из Excel» — FRAME

- **Статус:** Draft for decision
- **Дата:** 20.10.2026
- **Область:** `backend/src/materials`, `backend/src/price-list`, `backend/src/imports` (новый), `frontend/src/pages/Materials`
- **Для кого:** владелец продукта, тимлид, разработчик-исполнитель

Документ содержит критический разбор предыдущего предложения «импорт сметы + bulk-эндпоинт» с проверкой каждого утверждения по коду, три архитектурные альтернативы, детальный UX, финальный шаблон, правила матчинга, спецификацию API/DTO и поэтапный план с оценками.

---

## 0. TL;DR

1. **Главная ошибка предыдущего предложения** — оно проектирует «импорт нашего шаблона». В реальности прораб приносит **чужой** Excel от заказчика или сметчика. Если требовать перебить 300 строк в наш шаблон, мы автоматизируем не ту работу, которую хотели убрать. Приём произвольного `.xlsx` с авто-определением колонок — не «nice to have», а условие, при котором фича будет жить.
2. Парсить нужно **на сервере**: `exceljs@^4.4.0` уже в `backend/package.json:41` и уже используется в `reports/xlsx.service.ts`; `multer@2.0.2` уже лежит в `backend/node_modules` как зависимость `@nestjs/platform-express@^11.0.1` (`backend/package.json:35`). Новых пакетов не требуется.
3. Цены **никогда** не берём из файла как истину: `unitPrice` / `materialUnitPrice` — снапшот, который сервер копирует из `PriceItem` (`prisma/schema.prisma:117,123`; `materials.service.ts:151–170`). Файл — это «предложение», итог считает сервер.
4. **Нельзя делать импорт через `EstimateTemplate`**: `EstimateTemplateItem` (`schema.prisma:468–483`) не хранит `article` и `note`, а `apply()` пишет через `createMany` без проверки `isActive`/`kind`/`ownerId`, без транзакции и без отчёта (`estimate-templates.service.ts:119–131`). Импорт унаследует все эти дефекты.
5. **Нельзя гнать импорт через `ChangeRequest`**: `ADD_ROW` — одна заявка на одну строку с ручным подтверждением вторым лицом. 300 строк = 300 заявок и 300 аппрувов. Согласование имеет смысл **на уровне партии**, а не строки.
6. Нужны сущность `ImportBatch` и поля `Material.importBatchId / importRowNumber / externalKey`. Без них откат, повторный импорт и ответ на вопрос «кто это залил» невозможны в принципе. Это миграция Prisma (последняя в репозитории — `20261004165442_add_audit_log`).
7. `POST /materials/bulk` как основной канал **не годится**: в `main.ts` лимит тела не поднят, а express по умолчанию режет JSON на 100 КБ; 500 строк × ~250 байт ≈ 125 КБ уже не пролезают.
8. Импорт обязан быть **атомарным** (одна транзакция) и **идемпотентным** (уникальный `externalKey` + `status` у партии). «Половина сметы залилась» хуже, чем «не залилось ничего».
9. Импорт обязан уважать `isSpecLocked` (`schema.prisma:112`) и существующие фиксации: молчаливое обновление `specQuantity` там, где уже есть `MaterialFix`, искажает прогресс и деньги. Такие строки по умолчанию **не трогаем**.
10. Реалистичная оценка: **6–8 дней** на тонкий вертикальный срез и **10–12 дней** на описанный ниже объём с тестами. «2.5–3 дня» — недооценка в 3–4 раза, и причина не в коде, а в грязных файлах, матчинге и откате.

## 1. Проверка утверждений по коду

| Утверждение | Вердикт | Факт в коде |
|---|---|---|
| «Цены берутся из `PriceItem`, клиент их не присылает» | Подтверждено | В `create-material.dto.ts` ценовых полей нет; `materials.service.ts:151–170` достаёт `PriceItem` и копирует `price` в снапшот |
| «Снапшот нужен, потому что справочник меняется» | Подтверждено | `Material.unitPrice` / `materialUnitPrice` (`schema.prisma:117,123`), `PriceItem.isActive` (`:174`) |
| «Есть готовый bulk-эндпоинт» | **Опровергнуто** | В `materials.controller.ts` только `POST /materials` (42–48) и `POST /materials/price-item` (94–106). Массовой записи нет |
| «Можно писать через `createMany`, как в шаблонах» | Технически да, продуктово нет | `estimate-templates.service.ts:119–131` — `createMany` без транзакции, без проверки `isActive`, без дедупликации, без per-row ошибок |
| «`ChangeRequest` уже покрывает создание строк» | **Опровергнуто** | `ADD_ROW` объявлен (`schema.prisma:221–240`, whitelist `change.service.ts:407–421`), но текущий `materials.service.create()` заявок не создаёт — «обходной» путь и есть основной |
| «Шаблон сметы — подходящая точка входа» | **Опровергнуто** | `EstimateTemplateItem` теряет `article`/`note`; цены фиксируются при сохранении шаблона, а не при применении |
| «Excel-библиотеки надо добавить» | **Опровергнуто** | `exceljs ^4.4.0` на бэкенде, `xlsx-js-style ^1.2.0` и `pdfmake ^0.3.11` на фронте (`frontend/package.json:22,28`) |
| «Инфраструктура загрузки файлов есть» | **Опровергнуто** | Ни `FileInterceptor`, ни `multer` в коде приложения; multer 2.0.2 доступен транзитивно |
| «Матчинг можно сделать на фронте» | Спорно, отклонено | Фронт не знает правил `ownerId`/`isActive` и прав; два валидатора = гарантированный дрейф |
| «Лимита 500 строк достаточно» | Принято с оговоркой | 500 — рабочий предел партии в MVP; технически до 1000, см. §8.4 |

### 1.1 Долги, которые импорт обязан обойти (а не унаследовать)

1. **Цена не проверяется на принадлежность.** `materials.service.ts:151–170` делает `findUnique` по `id` и проверяет только `isActive`. Не сверяются ни `kind` (можно подставить материал в `priceItemId`, то есть «работу»), ни `ownerId` (можно прицепить чужую личную расценку). В `change.service.applyPayload` эти проверки есть. Импорт не должен повторять ошибку: он **резолвит** расценки сам и не доверяет `id` из файла.
2. **Общий справочник редактируем кем угодно.** `price-list.service.ts:23–27` строит `ownerFilter` как `OR [ownerId = userId, ownerId = null]`, и этот же фильтр используется в `updateItem`/`removeItem` (`:166–234`). Любой прораб может переименовать или снять с учёта общую расценку. Следствие для импорта: новые расценки создаём **только в личный справочник** (`ownerId = userId`), как в `createPriceItemWithCategory` (`materials.service.ts:645`).
3. **Поиск по справочнику ограничен 20 записями** (`price-list.service.ts:95`). Для матчинга нужен отдельный метод, переиспользовать `searchItems` нельзя.
4. **Нет уникальности расценок.** У `PriceItem` только `@@index([categoryId, ownerId])` (`schema.prisma:184`), нет `@@unique([ownerId, name, unit, kind])`. Дедупликация новых расценок должна быть в коде, иначе через месяц личный справочник превратится в свалку.
5. **`isSpecLocked` по умолчанию `true`** (`schema.prisma:112`), а `updateSpecQty` при блокировке отдаёт 409 (`materials.service.ts:297–299`). Импорт, создающий 300 заблокированных строк, оставит прораба без возможности исправить количество. Решение: импорт создаёт строки с `isSpecLocked = false`; блокировка — отдельное осознанное действие.
6. **`totalCost` — хранимое поле** (`schema.prisma:118`), пересчитывается от фактических фиксаций (`materials.service.ts:247–248`). При импорте оно `0`, и это правильно; плановая стоимость считается на лету как `specQuantity × (unitPrice + materialUnitPrice)`, отдельного поля не нужно.
7. **Нет `FileInterceptor` и нет лимита тела.** Нужно добавить `FileInterceptor` и поднять лимит JSON для эндпоинта предпросмотра из буфера обмена (`app.useBodyParser('json', { limit: '2mb' })` или эквивалент).

## 2. Главная развилка: чей файл мы принимаем

Есть два продукта с разной ценой:

**Продукт 1 — «наш шаблон».** Прораб скачивает xlsx, заполняет 300 строк, загружает. Ценность: он не набирает данные в веб-форме по одной строке, есть валидация. Стоимость: ~3–4 дня. Риск: если у него уже есть файл от заказчика, он всё равно перебивает 300 строк — либо не пользуется фичей, либо присылает файл в чат и просит «занеси руками».

**Продукт 2 — «любой xlsx».** Прораб кидает файл, который у него есть. Система определяет лист, шапку, колонки, нормализует, матчит расценки, показывает предпросмотр с суммами и спрашивает только про неоднозначное. Шаблон остаётся, но как «счастливый путь» для тех, кто начинает с нуля или хочет получить чистый файл с подсказками.

**Рекомендация: продукт 2, шаблон — вторичен.** Формулировка для владельца: *мы продаём не шаблон, мы продаём разбор чужого файла*. Всё остальное в этом RFC построено на этом решении: один матчер, один предпросмотр, два адаптера входа (файл и вставка из буфера обмена).

Побочный эффект: «вставка TSV из Excel» (Ctrl+V в браузере) должна идти через тот же предпросмотр. Это дешево (адаптер строк), закрывает случаи «файл пришёл в WhatsApp текстом» и «нужно быстро перенести 20 строк».

## 3. Архитектурные варианты

### 3.1 Вариант A — прямой импорт в `Material`

Поток: файл → парсинг → матчинг → предпросмотр → `POST /materials/bulk` → строки проекта.

**Плюсы:** минимум сущностей; один источник правды (смета = строки проекта); переиспользуются снапшоты и права; нет потери `article`/`note`; работает для «материал без работы» и «работа без материала».
**Минусы:** нет отката, нет повторного импорта без дублей, нет ответа «кто залил», нет истории. `POST /materials/bulk` с 500 строками не проходит по лимиту тела; клиентский парсинг требует второго валидатора.
**Что сломается через 6 месяцев:** в сметах появятся строки с `priceItemId = null` и `unitPrice = 0` (импорт «только в смету»), никто не сможет сказать, откуда они; повторная загрузка того же файла удвоит смету; откат — ручное удаление 300 строк в UI.

### 3.2 Вариант B — импорт в `EstimateTemplate` + `apply`

Поток: файл → шаблон → применение шаблона к проекту.

**Плюсы:** переиспользование существующего кода (`estimate-templates.service.ts`), появляется библиотека смет для повторного использования между объектами.
**Минусы:** `EstimateTemplateItem` (`schema.prisma:468–483`) **не хранит** `article` и `note` — артикулы из файла будут потеряны; цены в шаблоне — снапшот на момент импорта, а `apply()` копирует их как есть, поэтому через квартал применённая смета молча принесёт старые цены; `createMany` не проверяет `isActive`, значит в проект попадёт снятая с учёта расценка; ошибки `apply()` во фронте проглатываются (`Projects.tsx:193–195`), и пользователь не узнает, что часть строк не создалась; шаблоны принадлежат пользователю, а не объекту — коллективная работа ломается.
**Вывод:** вариант B отклоняется. Он выглядит дешёвым, но переиспользует код с дефектами и теряет данные из файла.

### 3.3 Вариант C (рекомендуемый, «C-lite») — партия импорта как журнал + кэш предпросмотра

Поток:

1. `POST /imports/estimates/preview` (multipart или JSON со строками) → сервер парсит, нормализует, матчит, **сохраняет** распознанные строки в `ImportBatch.preview` (Json) и возвращает предпросмотр.
2. Пользователь правит сопоставления в UI (только решения, не данные).
3. `POST /imports/estimates/:id/commit` → сервер **перечитывает строки из БД**, применяет решения, валидирует и пишет всё в одной транзакции, ставит `status = COMMITTED`.
4. `POST /imports/estimates/:id/rollback` → удаляет созданное, если по строкам нет фиксаций; иначе 409 со списком причин.

**Плюсы:** предпросмотр переживает F5; сервер — единственный источник правды (нельзя «подсунуть» другие строки на commit); commit идемпотентен по `status`; откат и повторный импорт реализуемы; аудит на уровне партии; «черновик» не дублирует смету целиком, поэтому нет рассинхрона двух моделей (в отличие от полного варианта C с отдельной таблицей строк-черновика).
**Минусы:** +1 таблица, +1 миграция, +1 экран, +1 состояние (`PREVIEW / COMMITTED / ROLLED_BACK / FAILED / CANCELLED`). Это ~1.5–2 дня сверх варианта A.
**Что сломается через 6 месяцев:** почти ничего нового — партии копятся, но это журнал, он и должен копиться. Риск один: `preview` в Json растёт; решается очисткой предпросмотров старше 30 дней.

### 3.4 Матрица сравнения

| Критерий | A (прямой) | B (через шаблон) | C-lite (партия) |
|---|---|---|---|
| Срок до первого результата | 4–5 дн | 3–4 дн | 6–7 дн |
| Срок до «не стыдно в прод» | 7–8 дн | 9–10 дн (надо чинить шаблоны) | 10–12 дн |
| Откат импорта | нет | нет | да |
| Повторный импорт без дублей | нет | нет | да (`externalKey`) |
| Сохранение `article`/`note` | да | **нет** | да |
| Цены на момент применения | да | **нет** | да |
| «Кто и когда залил» | нет | частично | да (партия + `AuditLog`) |
| Атомарность | руками | нет (`createMany`) | да (транзакция) |
| Новых сущностей | 0 | 0 | 1 таблица + 3 поля |
| Риск «половина сметы» | высокий | высокий | низкий |

**Рекомендация: C-lite, внедрять вертикальным срезом** (см. §9): сначала партия + предпросмотр + commit без отката, затем откат и diff.

## 4. Реальность полей: что реально приходит в файлах

Где я делаю вывод о поведении людей и типовых файлах, это **предположение** — конкретные файлы заказчиков не проверялись.

### 4.1 Грязь в файле

| Проблема | Частота (предположение) | Что делает импорт |
|---|---|---|
| Объединённые ячейки (ед. изм. «шт» на 5 строк, разделы) | очень часто | `exceljs` отдаёт значение только в левой верхней ячейке; остальные читаем как «наследовать сверху» **только для колонок ед.изм. и раздела**, для наименования — никогда (иначе склеим разные позиции) |
| Шапка не в первой строке, сверху логотип и «УТВЕРЖДАЮ» | часто | сканируем первые 30 строк, берём строку с максимальным score по синонимам заголовков |
| Двухуровневая шапка («Количество» → «всего / на объект») | иногда | берём нижний уровень, конфликт показываем в маппинге колонок |
| Итоговые строки «Итого», «НДС», «Всего по смете» внутри данных | часто | строки без наименования отбрасываем; «Итого/Всего/НДС/Транспортные» → отдельный список «похоже на итог», не импортируем, показываем в отчёте |
| Числа как текст: `1 200,50`, неразрывный пробел, `12,5 м2` в одной ячейке | часто | убрать все виды пробелов, `,` → `.`, вытащить первое число; `12,5 м2` → qty 12.5 + unit SQUARE_METER |
| Формулы вместо значений | часто | `cell.value = { formula, result }` — берём `result`, не `formula` |
| Скрытые строки и колонки | иногда | скрытые строки импортируем (они часть сметы), но помечаем в отчёте |
| Несколько листов: «Смета», «Материалы», «Свод», «Лист1» | часто | парсим все листы, считаем score «похожести на таблицу позиций», предлагаем лучший, даём выбрать другой |
| `.xls` (старый формат), `.csv`, экспорт Google Sheets | иногда | `.xlsx` и `.csv` — да; `.xls` — явный отказ с текстом «Сохраните как .xlsx» |
| Наименование в две строки внутри одной ячейки (`Alt+Enter`) | часто | перенос → пробел, но со следующей строкой таблицы не склеиваем |
| Раздел сметы отдельной строкой без количества | часто | используем как подсказку категории для новых расценок; в `note` не пишем |
| Одна позиция дважды в разных разделах | иногда | внутрифайловый дедуп по `externalKey`, см. §4.4 |

### 4.2 Единицы измерения — самая опасная часть

В системе ровно 10 единиц (`schema.prisma:88–99`, массив `UNIT_OPTIONS` в `Materials.tsx`): `PIECE (шт)`, `METER (м)`, `SQUARE_METER (м²)`, `CUBIC_METER (м³)`, `KILOGRAM (кг)`, `LITER (л)`, `TON (т)`, `BAG (мешок)`, `PACKAGE (упак)`, `SET (компл)`.

Чего нет: лист, рулон, погонный метр, «1000 шт», «кг/м²», «чел/час», «точка», «пролёт». Отсюда жёсткие правила:

- `м.п.`, `пог.м`, `п/м` → `METER` + **флаг «единица приведена приблизительно»** в предпросмотре.
- `кв.м`, `м2`, `м²`, `м.кв` → `SQUARE_METER`; `куб.м`, `м3` → `CUBIC_METER`.
- `уп`, `упак`, `пач`, `пачка` → `PACKAGE`; `меш`, `мешок` → `BAG`; `компл`, `к-т`, `набор` → `SET`.
- **`шт` ≠ `упак` ≠ `мешок`.** Автоконвертации нет: в модели нет коэффициента пересчёта. Если в файле `упак`, а в справочнике `шт`, матч **не предлагается автоматически** — только вручную и с предупреждением «цена за упак будет записана как цена за шт».
- Пустая/неизвестная единица — **не** «по умолчанию шт», а ошибка строки: «Укажите единицу измерения». Молчаливый `PIECE` портит суммы сильнее, чем пропущенная строка.

### 4.3 Артикулы, бренды, размеры

- Артикул — самый надёжный ключ, но только после нормализации: `uppercase`, удалить пробелы, дефисы, точки, `№`. Приведение кириллических `А/В/С/Е/К/М/Н/О/Р/Т/Х` к латинским **не делаем** (ложные склейки), но показываем предупреждение «артикул с кириллицей».
- Бренд (`Ceresit`, `Litokol`, `Кнауф`) не удаляем из названия, а выделяем в токены и сравниваем отдельно: несовпадение бренда режет score до 0.6, автопривязки не будет никогда.
- Числа в названии (`стяжка 50 мм` vs `стяжка 100 мм`, `клей 25 кг` vs `клей 5 кг`) критичны: если мультимножества чисел не совпадают, score ≤ 0.5.
- `kind` расценки обязателен при матчинге — защита от «плитка нашлась в работах».

### 4.4 Дубликаты

Три разных дубликата, лечатся по-разному:

1. **Внутри файла.** `externalKey = hash(normalized(name) | unit | normalized(article))`. При совпадении предлагаем «сложить количества» (по умолчанию), «оставить обе», «оставить первую».
2. **С существующей сметой проекта** — тот же `externalKey` против сохранённых строк. Действия: «пропустить» (по умолчанию, если есть фиксации), «обновить количество», «добавить как новую».
3. **С уже импортированным файлом** — `ImportBatch.fileHash` + предупреждение «этот файл уже импортирован 12.10 (партия #37), 128 строк». Не блокируем: файл мог измениться, тогда это честный новый импорт с диффом.

**Никогда не обновляем `specQuantity` там, где `totalUsed > 0`**, без явного подтверждения: это меняет `progressPercent` и плановую стоимость задним числом. Такие строки помечаются «есть факт 12 из 40» и по умолчанию не трогаются.

### 4.5 Несколько файлов на один проект

Сценарий реален: работы — один файл, материалы — второй, «допник» — третий. Поэтому:

- Партия = один файл. `ImportBatch` привязан к проекту, а не «заменяет смету».
- Повторный импорт делает дифф, а не перезапись.
- «Режима замены всей сметы» в MVP нет: он удалит фиксации.

### 4.6 Ограничение модели: 1 строка = 1 работа + 1 материал

`Material` хранит `priceItemId` (работа) и `materialItemId` (материал) в одной строке. «Одна работа + три материала» выражается только тремя строками, и стоимость работы утроится, если её продублировать. Правила:

- В шаблоне и предпросмотре работа указывается **только в первой строке** группы, остальные — «материал без работы».
- В предпросмотре предупреждение: «У работы X три строки материалов, стоимость работы учтена в первой строке».
- Группировка «работа ↔ материалы» — открытый вопрос (§11, Q7), в MVP не решается.

## 5. UX: пошагово

### 5.1 Точка входа

Кнопка «Импорт из Excel» в шапке `Materials` (страница уже существует, маршрут `App.tsx:99`). Видимость: `CUSTOMER` и `FOREMAN`, **скрыта для `VIEWER`**. Скрытие — только UX: сервер всё равно проверяет права, потому что `ObjectAccessGuard` не покрывает POST без `:id` в пути, и проверка живёт в сервисе (`materials.service.ts:62–82`, отказ для `VIEWER` — `:147`).

Импорт — **отдельная страница**, не модалка: `objects/:objectId/projects/:projectId/materials/import`. Причины: 500 строк в модалке — это фиксированная высота, вложенный скролл и потеря состояния; `Materials.tsx` уже ~2000 строк, и добавлять туда ещё 700 — плохая идея.

### 5.2 Экран 1 — загрузка

- Блок «Шаблон»: «Скачать пустой шаблон», «Скачать шаблон с моими расценками» (предзаполненный справочник), «Как заполнять» (3 строки текста, не PDF).
- Dropzone: `.xlsx` / `.csv`, ≤ 2 МБ, ≤ 500 строк. Ошибки формата — сразу, без загрузки на сервер (по расширению и размеру).
- Альтернатива: «Вставить из буфера» — textarea, пользователь делает Ctrl+V из Excel, получаем TSV → тот же предпросмотр.
- Если файл уже импортировался (совпадение `fileHash`), показываем жёлтую плашку с датой и количеством строк и две кнопки: «Всё равно загрузить», «Открыть ту партию».

### 5.3 Экран 2 — предпросмотр

Шапка с чипами: **Всего строк / Готово / Требуют решения / Новые расценки / Ошибки**. Дальше таблица (по 100 строк на страницу, клиентская пагинация):

| № | Наименование | Артикул | Кол-во | Ед. | Работа (справочник) | Материал (справочник) | Сумма, ₽ | Действия |
|---|---|---|---|---|---|---|---|---|

- Сопоставление показывается бейджем: «точно» (зелёный), «похоже — проверьте» (жёлтый), «не найдено» (серый), «конфликт единиц» (красный).
- Строка с ошибкой не блокирует остальные, но блокирует commit, пока не исправлена или не исключена.
- Массовые действия сверху: «Категория для новых работ: [select]», «Категория для новых материалов: [select]», «Создавать личные расценки: [x]», «Дубликаты: пропускать / обновлять количество / добавлять».
- Фильтры-табы: «Все», «Требуют решения», «Новые», «Дубликаты», «Ошибки».
- **Итог по смете** — главный элемент экрана: `Σ qty × (unitPrice + materialUnitPrice)` по строкам, готовым к импорту, и «изменение сметы: +1 245 300 ₽». Плюс отдельно: «строк с нулевой ценой: 7» (это будущая дыра в бюджете).

### 5.4 Сценарий «0 новых расценок»

Все строки сматчились. Экран показывает зелёный баннер: «Все 128 позиций найдены в справочнике. Итог: 1 245 300 ₽». Одна кнопка «Импортировать 128 позиций». Никаких чекбоксов и настроек. Это целевой путь, к нему надо стремиться: он должен занимать 15 секунд.

### 5.5 Сценарий «40 новых расценок»

Красная плашка: «40 позиций нет в справочнике. Без цены они попадут в смету с 0 ₽». Варианты (один блок, не 40 модалок):

1. «Создать 40 расценок в личном справочнике» — чекбокс, включён по умолчанию; цена берётся из колонки «Цена» файла, если она есть, иначе требуется ввод.
2. «Категория для всех новых работ» / «...материалов» — один select + «создать новую категорию».
3. Per-row правка — только для тех, где цены в файле нет.

Если цены в файле нет ни у одной из 40 — commit заблокирован, кнопка «Продолжить без цен» доступна только с явным чекбоксом «Я понимаю, что смета будет с нулевой стоимостью» и логируется в `AuditLog`.

### 5.6 Сбой в середине

Единственная правильная стратегия для 500 строк — **всё или ничего**. Причина: половина импортированной сметы хуже пустой, потому что прораб не знает, что уже залито, и заливает второй раз. Поэтому commit — одна транзакция; при ошибке:

- ничего не записано, партия остаётся в `PREVIEW`;
- UI возвращается на предпросмотр с подсветкой строк, которые сервер отверг (например, расценку успели снять с учёта между предпросмотром и commit);
- текст ошибки человеческий: «Позиция №43: расценка "Укладка плитки" снята с учёта 20.10. Выберите другую или создайте новую».

Частичный успех допустим только как **явный выбор** («импортировать 117 корректных, 11 оставить на потом»), и тогда создаётся вторая партия для остатка, чтобы откат был предсказуемым.

### 5.7 Результат

Экран: «Добавлено 128, обновлено 7, пропущено 3, создано расценок 40. Смета: 4 218 900 ₽ (+1 245 300 ₽)». Кнопки: «К смете», «Скачать протокол (.xlsx)», «Отменить импорт».

«Отменить импорт» доступно, только если по созданным строкам **нет фиксаций** и нет ручных правок; иначе кнопка неактивна с подсказкой «Есть 5 фиксаций — удалите строки вручную». Откат удаляет и созданные партией расценки, **если** они не используются другими строками (проверка `count` перед удалением; иначе оставляем и пишем в протокол).

### 5.8 Повторная загрузка через неделю

Файл тот же, но в смете уже работают. Предпросмотр показывает:

- «128 позиций уже есть в этой смете (импорт от 12.10, партия #37)»;
- «из них 34 имеют фиксации, 12 — заблокированы»;
- по умолчанию для строк с фиксациями выбирается «пропустить», для остальных — «обновить количество, если отличается»;
- явный дифф: «было 12,5 → стало 14,0 (м²)» с человеческим подтверждением;
- «в файле 6 новых позиций, 2 позиции исчезли — удалять не будем, покажите их в отчёте».

Ключевое: **импорт никогда не удаляет** строки, которых нет в файле. Иначе один неполный файл снесёт пол-сметы вместе с фиксациями.

### 5.9 Пустые состояния и тексты

- 0 строк в файле → «В файле не найдено ни одной позиции. Проверьте, что на листе есть колонки "Наименование" и "Количество"».
- Файл больше 500 строк → «В файле 812 строк. Разделите на две части или обратитесь к администратору» (и лог, чтобы понять реальный спрос).
- Все строки — дубликаты → «Все позиции уже есть в смете. Изменений нет».

## 6. Финальный шаблон

### 6.1 Листы

| Лист | Назначение | Видимость |
|---|---|---|
| `Смета` | данные: одна строка = одна позиция | видимый, активный |
| `Справочник` | плоский список активных расценок (общие + личные) для поиска глазами и ВПР | видимый |
| `Инструкция` | 12–15 строк: лимит 500, не объединять ячейки в данных, обязательные колонки, что будет с новыми расценками | видимый |
| `_meta` | `templateVersion=1`, `projectId`, `generatedAt`, `catalogsHash` | `veryHidden` |

`templateVersion` — не формальность: через год, когда колонок станет больше, импорт по `templateVersion` либо примет старый файл, либо скажет «шаблон устарел, скачайте новый». Без этого поля любая правка шаблона ломает загруженные ранее файлы молча.

### 6.2 Колонки листа «Смета»

| # | Колонка | Обяз. | Тип / правило |
|---|---|---|---|
| A | `№` | нет | текст/число, для сверки глазами, не участвует в логике |
| B | `Наименование работы` | да* | текст ≤ 300; *обязательно, если заполнена колонка E |
| C | `Артикул работы` | нет | **текстовый формат** (иначе `0012` → `12`) |
| D | `Ед. изм. работы` | да* | выпадающий список из 10 значений |
| E | `Количество` | да | число > 0, до 3 знаков после запятой |
| F | `Наименование материала` | нет | текст ≤ 300 |
| G | `Артикул материала` | нет | текстовый формат |
| H | `Ед. изм. материала` | усл. | обязательна, если заполнено F |
| I | `Примечание` | нет | текст ≤ 500, попадает в `Material.note` |
| J | `Цена работы (справочно)` | нет | число; **в смету не попадает как есть**, только для сверки и для создания новой расценки |
| K | `Цена материала (справочно)` | нет | то же |
| L | `ID работы` | нет | серый столбец, заполняется нами при генерации шаблона «с моими расценками»; приоритетный ключ матчинга |
| M | `ID материала` | нет | то же |

Почему `Количество` одно на строку, а не «кол-во работы + кол-во материала»: в модели `Material.specQuantity` — единственное количество, и работа, и материал считаются в тех же единицах строки. Разные единицы у работы и материала (работа в м², материал в шт) в одной строке — источник ошибок; такие позиции импортируются двумя строками.

### 6.3 Валидации в файле

- Список (Data Validation → List) для D и H: 10 значений из `UNIT_OPTIONS`. Ссылка на `Справочник` не работает в старых Excel напрямую через лист — используем **именованный диапазон** `ЕдиницыИзмерения` в `_meta` или inline-список (он короткий, 60 символов — безопасно).
- Числовая валидация для E: `decimal`, `> 0`, `<= 1000000`.
- Условное форматирование: B пустое и E заполнено → красная заливка B; F заполнено, H пустое → красная заливка H.
- Защита листа: заблокированы заголовки и `Инструкция`; разблокирован диапазон `B2:M501` (ровно 500 строк — столько же, сколько лимит импорта).
- `Freeze Panes` на `B2` (или `A2`), `AutoFilter` по заголовкам, ширины колонок, формат `# ##0,000` для E.
- Предзаполняем 500 строк: без этого Data Validation не сработает на новых строках, а пользователь не увидит ни списков, ни форматов.

### 6.4 Про выпадающие списки — почему НЕ список расценок

Соблазн: сделать в B выпадающий список всех расценок. Это плохая идея, и её надо зафиксировать письменно:

1. В Excel список из 500+ элементов в Data Validation практически нерабочий: нет поиска, нет скролла в привычном виде, ввод с клавиатуры фильтрует плохо.
2. Ограничение длины источника списка — 255 символов для inline и проблемы с кросс-листовыми ссылками в старых версиях; динамические именованные диапазоны через `OFFSET` ломаются при копировании листа.
3. Главное: **список не нужен**, если есть матчинг. Пользователь пишет название так, как привык, а система находит расценку. Список заставил бы его искать точную формулировку — то есть вернул бы ту работу, которую мы убираем.

Поэтому `Справочник` — это лист для человеческого поиска/фильтра и для формул-подсказок (`ВПР`/`XLOOKUP`), а точный матч делает сервер.

### 6.5 Генерация шаблона

`GET /imports/templates/estimate?projectId=...&withPrices=1&withIds=1` → `exceljs` (уже используется в `reports/xlsx.service.ts` и `reports.controller.ts:76–93`, паттерн отдачи буфера повторяем). Если `withIds=1`, в L/M подставляются `priceItemId` только для тех расценок, что доступны пользователю (`ownerId = null` или `ownerId = userId`) и `isActive = true`. `catalogsHash` в `_meta` = хеш списка id+price: если справочник изменился, импорт может сказать «в шаблоне устаревшие ID, но мы всё равно сматчили по названию».

## 7. Матчинг и нормализация: конкретные правила

### 7.1 Конвейер нормализации (одна функция, шарится парсером и матчером)

1. `NFKC`, `trim`, `lowercase`, `ё → е`.
2. Все виды пробелов (`\u00A0`, `\u202F`, тонкий) → обычный; повторные → один.
3. Разделители `.,;:/\\|—–-` между токенами → пробел; **внутри чисел** запятая → точка.
4. `Ø`, `⌀` → `d`; `×`, `х` (кириллица) между цифрами → `x`.
5. Вырезать мусорные обёртки (`далее — ...`, `см. приложение`, `ГОСТ ...`, `ТУ ...`) в отдельное поле `techRef` — в score не участвует.
6. Выделить и **не удалять** числа (как отдельные токены) и бренд-токены.
7. `articleNorm` = `uppercase`, убрать всё, кроме `[A-Z0-9А-Я]`.
8. `unitNorm` — по таблице синонимов (§4.2), результат — enum или `null`.

Стоп-токены для scoring (не влияют на схожесть, но сохраняются в названии): `устройство`, `монтаж`, `установка`, `работы`, `выполнение`, `согласно`, `проекту`, `всего`, `итого`.

### 7.2 Каскад сопоставления

| Шаг | Условие | Score | Автопривязка |
|---|---|---|---|
| 0 | `articleNorm` совпал и `kind` совпал | 1.00 | да |
| 1 | `nameNorm` полностью совпал, единица совместима | 1.00 | да |
| 2 | Jaccard по токенам ≥ 0.85 **и** числа совпали **и** единица совпала | 0.85–0.99 | предлагается, требует подтверждения |
| 3 | 0.65 ≤ score < 0.85 | 0.65–0.85 | только подсказка, не выбрано |
| 4 | < 0.65 или конфликт чисел/единиц | — | «новая расценка» |

`score = 0.6 × Jaccard(tokens) + 0.4 × Dice(trigrams)`, затем штрафы:

- числа не совпали → `min(score, 0.50)`;
- бренд не совпал → `min(score, 0.60)`;
- единица несовместима → `min(score, 0.40)`;
- `kind` не совпал → кандидат не рассматривается вообще.

Кандидаты: предфильтр по `kind` + `isActive` + (`ownerId = null` или `ownerId = userId`), затем по префиксу первого значимого токена (3 символа) и по единице; скорим не более 200 кандидатов, показываем 5 лучших. На текущих объёмах это доли секунды; при 50k расценок переходим на `pg_trgm` + GIN — отдельная задача.

### 7.3 Как избегать ложных склеек

- **Никогда** не матчить по «содержит» без учёта чисел: `Труба 50` находится в `Труба 50x3`, но не в `Труба 100`.
- **Никогда** не выбирать «лучшего кандидата», если score < 0.65, даже если он единственный.
- **Никогда** не матчить между `kind` (материал ↔ работа) и между несовместимыми единицами.
- Всегда показывать в предпросмотре **категорию** найденной расценки: если в строке «плитка», а категория «Штукатурные работы», человек увидит ошибку мгновенно, хотя алгоритм был уверен.
- Если два кандидата в пределах 0.05 — не выбираем ни одного, показываем оба (часто: «Клей плиточный 25 кг» и «Клей плиточный усиленный 25 кг»).
- Дедуп новых расценок перед созданием: `nameNorm + unit + kind` в личном каталоге; при совпадении не создаём вторую, а переиспользуем существующую.

### 7.4 Детерминизм и тесты

Матчер — чистая функция без БД внутри (`matchRows(rows, catalog) → matches`), БД только поставляет каталог. Держим эталонный набор из 20–30 реальных (обезличенных) строк и проверяем, что после правок нормализации результаты не поехали. Без снэпшот-теста матчинг деградирует тихо.

| `POST` | `/imports/estimates/:id/cancel` | отменить предпросмотр |
| `GET` | `/imports/estimates?projectId=` | история импортов проекта |
| `GET` | `/imports/estimates/:id/report.xlsx` | протокол (создано/пропущено/ошибки) |

`POST /materials/bulk` **не вводим**. Причины: (а) не решает задачу целиком (нет матчинга и предпросмотра), (б) провоцирует клиентов писать свои парсеры и слать «сырые» строки, (в) дублирует валидацию, (г) не имеет идемпотентности. Массовая запись живёт внутри `commit`, в одной транзакции.

Лимиты: `rowsTotal ≤ 500` (жёстко), ≤ 500 решений, тело ≤ 1 МБ (лимит JSON поднимаем только для этого роута), файл ≤ 2 МБ. При превышении — `413` с понятным текстом.

### 8.5 Транзакция

Всё внутри `prisma.$transaction`:

1. `updateMany({ where: { id, status: 'PREVIEW' }, data: { status: 'COMMITTING' } })` → если `count !== 1`, `409` («партия уже обрабатывается или отменена»). Это даёт идемпотентность против двойного клика без отдельного мьютекса.
2. Загружаем `preview` из БД (доверяем только ему, не телу запроса).
3. Для каждого `IMPORT` резолвим `PriceItem` **внутри транзакции**: `isActive`, `kind`, `ownerId ∈ {null, userId}`; цену берём из БД.
4. Создаём/обновляем `Material` со снапшотом цены, `isSpecLocked = false`, `importBatchId`, `importRowNumber`, `externalKey`, `totalCost = 0`.
5. Создаём новые `PriceItem` (личные, `ownerId = userId`, дефолтная категория, дедуп перед созданием).
6. `status = COMMITTED`, счётчики и `report` (Json), `committedAt`.
7. `audit.log(userId, 'estimate_import', batchId, 'COMMIT', null, summary)` — `AuditService.log` требует `entityId: number` (`audit.service.ts:16–34`), `batchId` подходит.

500 строк в одной интерактивной транзакции — секунды, не минуты. Для 5000 понадобится job/worker; в MVP не нужно.

### 8.6 Идемпотентность и модель данных

```prisma
model ImportBatch {
  id              Int      @id @default(autoincrement())
  projectId       Int
  importedById    Int
  fileName        String?
  fileHash        String?
  templateVersion Int?
  status          String   @default("PREVIEW") // PREVIEW|COMMITTING|COMMITTED|ROLLED_BACK|FAILED|CANCELLED
  rowsTotal       Int      @default(0)
  createdCount    Int      @default(0)
  updatedCount    Int      @default(0)
  skippedCount    Int      @default(0)
  pricesCreated   Int      @default(0)
  preview         Json?
  report          Json?
  createdAt       DateTime @default(now())
  committedAt     DateTime?
  @@index([projectId, createdAt])
}
```

`Material` + `importBatchId Int?`, `importRowNumber Int?`, `externalKey String? @db.VarChar(64)`, `@@unique([projectId, externalKey])`, `@@index([projectId, importBatchId])`.

В SQL `UNIQUE` допускает много `NULL`, поэтому ручные строки не конфликтуют. При этом `externalKey` обязателен для всех импортированных строк — иначе повторный импорт снова создаст дубли.

### 8.7 Прямая запись против `ChangeRequest PENDING`

Аргументы за прямую запись (рекомендация):

1. `ADD_ROW` — одна заявка на строку (`change.service.ts:407–421`); 300 строк = 300 записей + 300 решений человека. Это не автоматизация, а её имитация.
2. `ChangeRequest` не хранит, откуда строка пришла (`batchId` нет), значит «согласовать смету целиком» технически невозможно.
3. Смета — план, а не факт. `CUSTOMER` её и так видит, `FOREMAN` — автор. Аппрув по строкам оправдан для `CHANGE_QTY`/`CHANGE_PRICE` **уже работающей** строки, а не для первичного наполнения.
4. Блокировка импорта аппрувом убивает adoption: прораб не начнёт работу, пока заказчик 300 раз не нажмёт «одобрить».

Вместо этого: прямой commit + `AuditLog` + журнал партии + уведомление «прораб импортировал 312 позиций на 4.2 млн, откат доступен 7 дней». Позже (Фаза 3) — режим «партия на согласовании»: одна кнопка «Утвердить импорт», строки `PROPOSED` не попадают в итоги до аппрува. Это правильная гранулярность, но отдельная фича.

Что нужно добавить в существующий код:

- `materials.controller.ts` — ничего не меняем, импорт живёт в своём контроллере.
- `materials.service.ts` — вынести приватный хелпер снапшота (`resolveSnapshot(priceItemId, kind, userId, tx)`) и переиспользовать в `create()`, `update()` и в импорте. Заодно закрыть долг §1.1(1): сейчас `create()` не проверяет `kind`/`ownerId`.
- `main.ts` — `app.useBodyParser('json', { limit: '1mb' })` (или `NestFactory.create(AppModule, { bodyParser: true })` + `app.useBodyParser`), иначе JSON-вариант предпросмотра на 500 строках упадёт на 100 КБ.

## 10. Что бы я сделал иначе (критика предложения)

1. **Не заставлять прорабов перебивать в наш шаблон.** Это главное. Предложение оптимизировало ввод, а не перенос. Прораб не будет набирать 300 строк заново, если файл уже есть; он либо откажется от фичи, либо попросит «занеси». Приём чужого файла — не расширение, а суть.
2. **Никакого импорта «в шаблон сметы».** Шаблон — это библиотека для повторного использования, а не транзитная станция. Заставить данные пройти через модель, которая теряет `article`/`note` и морозит цены, — значит заплатить за перенос данными.
3. **Предпросмотр — не модалка.** 500 строк в модалке — это гарантированные баги с состоянием и скроллом. Отдельная страница + серверное состояние.
4. **Матчинг на сервере, а не в браузере.** Одна реализация, тестируемая, с доступом к `ownerId`/`isActive`, без риска, что фронт и бэк разойдутся в правилах.
5. **Не «создавать расценки галочкой на всё» без дедупа.** Иначе через месяц личный справочник — 400 почти одинаковых строк, и матчинг начнёт деградировать по причине, которую мы сами создали.
6. **Не «обновлять количество» молча там, где есть фиксации.** Это правка истории задним числом.
7. **Не обещать 3 дня.** Правильная оценка — 10–13, и лучше сказать это сразу, чем через неделю «ещё два дня».
8. **Не делать выпадающий список расценок в Excel.** Технически возможно, практически бесполезно.
9. **Не гнать импорт через `ChangeRequest`.** Согласование — на уровне партии.
10. **Не игнорировать цену в файле.** Прораб приносит смету заказчика, где цена договорная. Молча заменить её ценой из справочника — потерять доверие к системе. Правильно: показать разницу и предложить выбор (справочник / личная расценка по цене файла / только в смету).
11. **Не проектировать идемпотентность «на глаз».** `externalKey` + `status` партии — это 2 часа работы и спасённые нервы при первом же повторном импорте.
12. **Не забыть про лимит тела.** «Отправим 500 строк JSON-ом» звучит нормально, пока не выясняется, что express режет на 100 КБ.

## 11. Решения и открытые вопросы

### 11.1 Принятые решения

1. Импорт принимает **произвольный** `.xlsx`/`.csv`; шаблон — опциональный «счастливый путь».
2. Парсинг, нормализация и матчинг — **только на сервере**, `exceljs` + существующий `multer`.
3. Архитектура — **C-lite**: `ImportBatch` (журнал + кэш предпросмотра) + `Material.importBatchId/externalKey`.
4. `POST /materials/bulk` **не вводим**; массовая запись — внутри `commit`.
5. Цены всегда резолвятся **из `PriceItem`** на момент commit; цена из файла используется только для создания личной расценки или (явным выбором) для строки без расценки.
6. Новые расценки создаются **только в личный справочник** (`ownerId = userId`), с дедупом по `nameNorm + unit + kind`.
7. Commit **атомарный**: всё или ничего; частичный успех — только явным выбором и отдельной партией для остатка.
8. Импорт **никогда не удаляет** существующие строки, которых нет в файле.
9. `isSpecLocked = false` для созданных импортом строк.
10. Строки с `totalUsed > 0` не получают новое количество без явного подтверждения.
11. VIEWER не может импортировать (проверка в сервисе, не только в UI).
12. Лимит: 500 строк, 2 МБ файл, 1 МБ JSON, `413` при превышении.
13. Идемпотентность: `@@unique([projectId, externalKey])` + переход `PREVIEW → COMMITTING` через `updateMany`.
14. Импорт пишет `AuditLog` (`entity='estimate_import'`, `entityId=batchId`); откат доступен 7 дней и только без фиксаций.
15. Ошибка в строке блокирует commit, но не мешает работе с остальными строками.

### 11.2 Открытые вопросы к владельцу

- **Q1.** Может ли `FOREMAN` заливать смету **без** согласования с `CUSTOMER`? Если нет — нужен режим «партия на согласовании» в MVP, это +2 дня.
- **Q2.** При расхождении цены в файле и справочнике что считаем истиной по умолчанию: справочник (моё предложение) или цену файла?
- **Q3.** Новые расценки: сразу в личный справочник (моё предложение) или в общий с модерацией? (Общий справочник сейчас правит любой — §1.1(2).)
- **Q4.** 500 строк — предел или надо 2000? От ответа зависит, нужен ли фоновый job.
- **Q5.** Нужен ли откат импорта после появления фиксаций? Я предлагаю «нет, только ручное удаление».
- **Q6.** Поддерживаем `.xls` (старый формат) или отказываем с просьбой сохранить как `.xlsx`?
- **Q7.** Нужна ли группировка «работа ↔ N материалов» в модели? Сейчас 1 строка = 1 работа + 1 материал.

## Приложение B. Чек-лист приёмки

1. Файл заказчика (не наш шаблон), 132 строки, шапка на 7-й строке, объединённые ячейки — импортируется, предпросмотр даёт ≥ 90% автопривязок.
2. Повторная загрузка того же файла не создаёт дублей; для 34 строк с фиксациями по умолчанию «пропустить».
3. Файл с 40 новыми расценками: создаются 40 личных расценок, дублей в справочнике нет, категория проставлена.
4. Ошибка в строке (неизвестная единица) блокирует commit; после исправления импорт проходит.
5. Двойной клик по «Импортировать» не создаёт вторую партию.
6. `VIEWER` получает 403 на `preview` и `commit`.
7. Откат партии без фиксаций удаляет строки и созданные расценки; с фиксациями — 409 с человеческим текстом.
8. В `AuditLog` есть запись о партии с количеством строк и суммой.
9. Смета после импорта открывается, суммы совпадают с предпросмотром до копейки.
10. Шаблон скачивается, открывается в Excel, списки единиц работают, защита не мешает вводу данных.
